## 绑定授权与隔离

Skills 平台的安全基石是**按授权绑定**：每一个用户授权（consent grant）把「一个 Agent + 一个已授权用户 + 一项能力」绑成专属、不可交叉的三元关系。这种设计天然隔离了不同 Agent、不同用户的数据和权限，无需复杂的中央权限管理系统。

**核心特点：**

- **天然隔离**：每个 consent grant 的用户数据只对其绑定的 Agent 可见，跨 Agent 访问被永久拦截
- **无权限膨胀**：不存在 Admin、Super User 等特殊角色，权限明确且固定，按能力（scope）限定
- **审计友好**：每个授权关系清晰易追踪，便于日志审计和合规检查

## 双层认证

Skills 平台采用 **API Key + 用户授权（consent grant）** 的双层认证机制：

1. **API Key** — 标识 Agent 身份（连接层），由 Agent 应用方保管
2. **用户授权（consent grant）** — 标识一个已授权的外卖用户，**一个 consent grant 对应一个用户、默认 90 天有效**，通过绑定流程（SMS 验证码 / H5）获得

> **每个用户必须本人授权一次。** 平台不提供 Admin 静默绑定 —— 不存在任何后台凭据可以替用户跳过授权（旧版 `ADMIN_SECRET` / 受信绑定已移除）。用户只能通过 `request_user_bind`（SMS 默认 / H5）发起、再由本人 `verify_user_bind` 完成授权。

### API Key（Agent 识别）

- **前缀**：`clw_` 开头，后接随机字符，例如 `clw_a1b2c3d4...`
- **存储**：服务端只存哈希、不保留明文，每次请求按哈希比对
- **颁发**：在 [Portal](https://console.hicaspian.com/agents) 创建 Agent 时生成，**仅显示一次**，遗失需重新生成
- **使用**：在连接层 HTTP Header 中作为 `Authorization: Bearer {API_KEY}` 传入，标识调用方 Agent

### 用户授权 consent grant（用户识别）

- **前缀**：`cg_` 开头
- **一对一**：一个 consent grant 对应一个用户（绑「Agent + 用户 + 能力」三元关系）
- **有效期**：默认 **90 天**；到期或轮换后需用户重新绑定
- **来源**：用户通过绑定流程（SMS 验证码 / H5）**本人授权**后获得；`verify_user_bind` 成功返回 `consent_grant_id`、`scopes`、`expires_at`（ISO 8601）
- **存储**：明文仅本次返回一次，落库仅存哈希，请妥善保存
- **传递**：作为每个 MCP 工具的 `consent_grant_id` 参数传入（不放进 body，也不走请求头）
- **失效**：到达 `expires_at` 过期，或被 `revoke_user_bind` 撤销后即时失效，需重新绑定获取新的

## 数据加密

Skills 平台对所有敏感数据进行分层加密 / 哈希，确保即使数据库泄露也无法直接还原关键信息：

<Tabs>
  <Tab title="用户身份">
    **用户 ID 加密**
    - 算法：AES-256-GCM
    - 密钥：由服务端安全生成和管理
    - 场景：用户 ID 在数据库中以密文存储
    - 解密权限：仅绑定的 Agent 可解密其对应的用户数据
  </Tab>

  <Tab title="电话号码">
    **电话号码去重 / 去识别**
    - 算法：SHA-256（单向哈希）
    - 用途：检测重复绑定、去识别存储
    - 特点：单向哈希，无法反向解密
    - 场景：绑定验证后，电话号码以哈希形式存储
  </Tab>

  <Tab title="凭据哈希">
    **API Key 与 consent grant 哈希**
    - 算法：单向哈希
    - 用途：验证 Agent 与用户授权的合法性
    - 特点：数据库中无法查看明文凭据
    - 场景：每次请求时，服务端对传入的 API Key / consent_grant_id 哈希后与数据库比对
  </Tab>
</Tabs>

## Agent-User 隔离

Skills 平台在数据访问层强制执行严格的隔离策略：

```
访问规则：
┌─────────────────────────────────────────────┐
│ Agent A 的 API Key + consent grant 1        │
│ → 只能访问 User 1 的数据                     │
│ → 不能访问 User 2 的数据                     │
│ → 不能访问 Agent B 的数据                   │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│ Agent B 的 API Key + consent grant 2        │
│ → 只能访问 User 2 的数据                     │
│ → 不能访问 User 1 的数据                     │
│ → 不能访问 Agent A 的数据                   │
└─────────────────────────────────────────────┘
```

**实现细节：**

1. 每个授权类请求都携带 API Key 和 `consent_grant_id`
2. 服务端验证 API Key，解析出 `agent_id`
3. 服务端验证 `consent_grant_id`，定位已授权用户与其授权能力
4. 数据库查询条件：`WHERE agent_id = ? AND user_id = ?`
5. 任何跨越这两个条件的查询都会被拒绝（授权属于其它能力 / 服务商返回 `CONSENT_GRANT_WRONG_CAP`，能力未开通返回 `CAP_NOT_BOUND`）

**关键节点：**

| 事件 | 触发 | 描述 |
|------|------|------|
| 铸造 | `verify_user_bind` 成功 | 返回 `consent_grant_id` + `scopes` + `expires_at`；明文仅此一次 |
| 正常使用 | `expires_at` 之前 | 授权类请求正常处理 |
| 重授权即轮换 | 同一用户再次成功绑定 | 铸造新的 `consent_grant_id`，旧的立即失效 |
| 失效 | 到达 `expires_at` 或被撤销 | 即时失效，请求返回 `CONSENT_GRANT_INVALID` / `CONSENT_GRANT_EXPIRED` |
| 重新绑定 | 失效后 | 重新走绑定流程获取新的；用户的地址、订单历史等数据保留，重新授权后自动可用 |

## 认证失败处理

认证 / 授权失败统一返回 `{"error": {"code", "message"}}` 结构，并附相应的 HTTP 状态码：

<CardGroup cols={2}>
  <Card title="401 Unauthorized" icon="lock">
    **凭证缺失或无效**
    - 缺少 API Key（`AUTH_REQUIRED`）
    - API Key 无效或已禁用（`AUTH_INVALID`）
    - 缺少 consent_grant_id（`CONSENT_GRANT_REQUIRED`）
    - consent_grant_id 无效或已过期（`CONSENT_GRANT_INVALID` / `CONSENT_GRANT_EXPIRED`）
  </Card>

  <Card title="403 Forbidden" icon="ban">
    **无权限访问**
    - 授权属于其它能力 / 服务商（`CONSENT_GRANT_WRONG_CAP`）
    - 当前 Agent 未开通该能力（`CAP_NOT_BOUND`）
  </Card>

  <Card title="429 Too Many Requests" icon="hourglass">
    **速率限制**
    - 在限制时间内请求过多（`RATE_LIMITED`）
    - 每个 Agent 独立限流（下单 10 次/分钟，其他 60 次/分钟）
  </Card>

  <Card title="统一错误格式" icon="circle-x">
    **`{"error": {"code", "message"}}`**
    - 所有认证 / 授权 / 业务错误同构
    - 完整错误码见 [错误处理](/gateway/error-handling)
  </Card>
</CardGroup>

认证链与各端点的认证级别详见 [认证机制](/gateway/authentication)。

## 安全最佳实践

<Tabs>
  <Tab title="Agent 应用端">
    - **保管 API Key**：存储在安全的环境变量或密钥管理系统中，不要提交到版本控制
    - **保管 consent_grant_id**：安全存储用户授权凭证（明文仅返回一次），涉及用户敏感数据
    - **HTTPS only**：所有与 Skills API 的通信必须使用 HTTPS
    - **轮换与撤销**：在 Portal 按需轮换 / 禁用 API Key（立即失效）；consent grant 重授权即轮换，并可随时 `revoke_user_bind` 撤销
    - **错误处理**：捕获 401/403 错误，提示用户重新认证或重新绑定
  </Tab>

  <Tab title="服务端">
    - **验证所有请求**：不信任任何客户端声称的身份，总是校验 API Key 与 consent_grant_id
    - **日志脱敏**：日志中不记录完整的 API Key 或 consent_grant_id，仅记录前缀或哈希
    - **速率限制**：每个 Agent 有独立的速率限制，防止滥用
    - **密钥轮换**：定期轮换数据库密钥，支持旧密钥的平滑过渡
    - **审计日志**：记录所有认证尝试（成功和失败），便于合规检查
  </Tab>

  <Tab title="绑定流程">
    - **防重放攻击**：SMS 验证码一次性使用，防止重复提交
    - **限制尝试次数**：超过一定次数的失败验证后，锁定该电话号码一段时间
    - **验证码过期**：生成的验证码数分钟后自动失效
    - **号码校验**：校验电话号码格式，防止恶意输入
    - **H5 回调校验**：H5 授权模式下校验回调来源，防止伪造
  </Tab>
</Tabs>

## 常见问题

<details>
<summary>一个 consent grant 可以在多个 Agent 中使用吗？</summary>

**不可以**。consent grant 绑定到「Agent + 用户 + 能力」三元关系，只对铸造它的那个 Agent 有效。每个 Agent 应用方都需要分别为该用户走一次绑定流程，拿到各自的 `consent_grant_id`。跨绑定的访问会被拒绝（`CONSENT_GRANT_WRONG_CAP`）。

</details>

<details>
<summary>API Key 泄露了怎么办？</summary>

立即在 [Portal](https://console.hicaspian.com/agents) 禁用该 API Key，系统将自动停止所有使用该 Key 的请求；随后生成新的 API Key 并更新应用配置。数据库中只存 API Key 的哈希，攻击者无法直接利用泄露的哈希值。

</details>

<details>
<summary>consent grant 过期或撤销后数据会丢失吗？</summary>

**不会**。consent grant 只是访问凭证；过期或撤销后，用户重新走绑定流程（同一手机号）即可获得新的 `consent_grant_id`，地址、订单历史等数据保留并自动恢复可用，不会因凭证失效而删除。

</details>

<details>
<summary>支持 API Key 权限分级吗？</summary>

Skills 平台不提供 API Key 权限分级。访问范围由每个 consent grant 的能力（scope）限定——一个授权只能操作其所属能力下、其绑定用户的数据。如果需要更细粒度的权限控制，建议在 Agent 应用层面实现。

</details>
