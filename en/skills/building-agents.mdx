## Overview

This guide will walk you through using the Clawdot Gateway to build a complete local life Agent from scratch. By following best practices and handling edge cases, you will be able to create a robust, user-friendly application.

The Gateway exposes its capabilities as **MCP (Model Context Protocol) tools** — once you connect, you see 18 tools and chain them, from binding/consent through finding shops and picking items, all the way to preview, order, and signing. Every example below is given as a **tool name + JSON arguments** (every business tool carries `consent_grant_id`, except the binding tools).

## Architecture Design

A complete local life Agent consists of the following modules:

```
┌─────────────────────────────────────────────┐
│         User Interaction Layer (Agent App)  │
│  Claude Desktop / Kimi / DingTalk / Custom  │
└────────────────────┬────────────────────────┘
                     │
┌────────────────────▼────────────────────────┐
│        Business Logic Layer (Your Code)     │
│  • User consent mgmt    • Order chain mgmt  │
│  • Local caching        • Error handling    │
└────────────────────┬────────────────────────┘
                     │
┌────────────────────▼────────────────────────┐
│     Clawdot Gateway (MCP)                   │
│  • Shop search      • Order preview/create  │
│  • Menu queries     • Payment sign          │
│  • Address mgmt     • Coupon management     │
└─────────────────────────────────────────────┘
```

<Info>
The Gateway exposes **18 MCP tools** over Streamable HTTP, covering the full local-life flow from binding/consent to ordering and payment. The connection, grouping, and ordering sequence of the tools are in the [MCP Overview](/en/mcp/overview).
</Info>

## Step 1: Get API Key and Connect to MCP

<Steps>
  <Step title="Create an Agent in the console">
    Visit [Clawdot Console](http://console.hicaspian.com/agents), create an Agent and enable the delivery capability for it. Agents and API Keys are both managed in the console.
  </Step>

  <Step title="Copy API Key">
    System generates an API Key (starting with `clw_`), **displayed only once** — immediately copy and save to a secure location. The server only stores a hash; if lost, you must regenerate it.
  </Step>

  <Step title="Configure the API Key in your MCP client">
    The gateway serves MCP over **Streamable HTTP** (FastMCP), with the endpoint `http://eleme-gateway.hicaspian.com/mcp/v1`. Put the API Key into your MCP client's connection headers:

    ```json
    {
      "mcpServers": {
        "clawdot-eleme": {
          "url": "http://eleme-gateway.hicaspian.com/mcp/v1",
          "type": "http",
          "headers": {
            "Authorization": "Bearer clw_your_api_key"
          }
        }
      }
    }
    ```

    <Warning>
    Do not commit the API Key to a Git repository or hard-code it into your source; inject it via environment variables or a secrets manager.
    </Warning>
  </Step>
</Steps>

<Info>
The API Key identifies the **Agent**, passed at the **connection layer** via the `Authorization: Bearer clw_...` header — required on every MCP request. To act on user resources, you also need the **user consent grant** obtained in the next step, which is passed as the `consent_grant_id` tool argument (not a header). See [Authentication](/en/gateway/authentication).
</Info>

## Step 2: Get User Consent

Acting on user resources (search shops, place orders, query addresses, etc.) requires two-layer authentication: the connection-layer API Key identifies the Agent, and the **user consent grant** identifies the authorized delivery user. After a user completes a binding flow once, you get a `consent_grant_id` (prefixed `cg_`) and pass it as an argument on every subsequent business tool call.

Binding supports two modes: `sms` (sends a verification code to the phone) and `h5` (returns an authorization link the user logs in through). The binding tools `request_user_bind` / `verify_user_bind` are the entry point for obtaining consent — they **only need the Agent identity (connection-layer API Key) and take no `consent_grant_id`**. The example below uses `sms`.

### Binding Flow

First, initiate binding; the gateway sends a verification code to the user's phone:

```json
// tool: request_user_bind — start SMS binding, user receives a code
{
  "phone": "18800000000",
  "auth_type": "sms"
}
// → { "bind_id": "...", "expires_in": 300, "masked_phone": "188****0000" }
```

Second, after the user tells you the code, confirm the binding to mint the `consent_grant_id`:

```json
// tool: verify_user_bind — verify the code, exchange for consent_grant_id
{
  "auth_type": "sms",
  "bind_id": "<bind_id from the previous step>",
  "code": "123456"
}
// → { "bound": true, "consent_grant_id": "cg_...", "scopes": [...], "expires_at": "..." }
```

Once you have the `consent_grant_id`, keep it safe — its plaintext is returned only once and only a hash is stored. Pass it as an argument on every subsequent business tool call.

<Note>
**H5 mode** is also supported: `request_user_bind(auth_type="h5")` returns an `h5_url` (valid for ~300s); hand the link to the user to open and authorize. Then poll with `verify_user_bind(auth_type="h5", request_id=...)` — `pending` means not yet done, and `bound=true` returns the `consent_grant_id`. You may also pass `callback_url` to `request_user_bind`, and the gateway will POST a callback (`event=user_bind`) once authorization completes. Full fields in [Initiate Binding](/en/mcp/user/bind-request) and [Confirm Binding](/en/mcp/user/bind-verify).
</Note>

<Info>
The `expires_at` returned on success is the consent expiry (ISO 8601). **Re-authorization rotates the grant**: each successful binding for the same user mints a new `consent_grant_id` and immediately invalidates the old one. Consent can be revoked any time via `revoke_user_bind`, after which the old `consent_grant_id` is invalidated immediately.
</Info>

## Step 3: Core Business Flow

Implement the complete chain from search, browse, quote, preview, to order and sign. The whole chain is **stateful**: each step's returned ID must be passed verbatim to the next — never fabricate one or mix IDs across chains.

```
search_shops → get_shop_menu → quote_cart → select_address
            → preview_order → create_order → get_sign_action
```

<Warning>
All amount fields are in **cents (integer)**, not yuan. For example `payable_price: 1500` means ¥15.00.
</Warning>

Every business tool call below carries the `consent_grant_id` argument (from Step 2).

### Phase 1: Search Shops

```json
// tool: search_shops — search / browse nearby shops
{
  "consent_grant_id": "cg_your_consent_grant",
  "keyword": "iced latte",
  "address_id": "addr_..."
}
// → { "shops": [ { "shop_id": "...", "cart_id": "...", "name": "...", "rating": ..., "min_order_amount": ... } ], "next_offset": ... }
```

Without `keyword` it is **browse mode** (up to 20 nearby shops) with distance, rating, delivery fee, min-order and other decision fields; with `keyword` (shop name / category / item name) it is precise search (~5 shops). Browse mode accepts `offset` for paging: pass `offset: 0` first, keep paging with the returned `next_offset` until `shops` is empty.

Each result carries a `shop_id` and a `cart_id`: the `cart_id` already encapsulates that shop plus the delivery coordinates, and is the entry point for the later `get_shop_menu` / `quote_cart` / `preview_order` — pass it **verbatim**. Full fields in [Search Shops](/en/mcp/shops/search).

### Phase 2: View Menu Details

```json
// tool: get_shop_menu — get a shop's menu
{
  "consent_grant_id": "cg_your_consent_grant",
  "shop_id": "<from search>",
  "cart_id": "<from search>",
  "keyword": "latte"
}
// → { "categories": [...], "items": [ { "item_id": "...", "sku_id": "...", "ingredient_options": [...] } ], "has_more": false }
```

Menus can be very large (100+ items); use `keyword` or `limit` / `offset` for progressive disclosure and check `has_more` for more. To order, you MUST use the `item_id` / `sku_id` returned by `get_shop_menu` (plus `ingredient_option_ids` for specs / add-ons). Full fields in [Shop Menu](/en/mcp/shops/detail); the spec / attribute / add-on system is in [Item Specs](/en/gateway/item-specs).

### Phase 3: Prepare Delivery Address

The address flow = search POIs for a single-use `token` → register for an `address_id`. First search addresses:

```json
// tool: search_addresses — search address POIs, get suggestions (with single-use token)
{
  "consent_grant_id": "cg_your_consent_grant",
  "keyword": "Optics Valley",
  "lat": 30.5,
  "lng": 114.4
}
// → { "saved_addresses": [ { "address_id": "...", ... } ], "suggestions": [ { "token": "...", ... } ] }
```

`saved_addresses[]` are already-saved addresses whose `address_id` can be reused directly; for a new address, take a `suggestions[].token` and pass it as `select_address`'s `suggestion_token` to register it:

```json
// tool: select_address — register/select an address by suggestion_token, get address_id
{
  "consent_grant_id": "cg_your_consent_grant",
  "suggestion_token": "<suggestion_token from the previous step>",
  "contact_name": "Zhang San",
  "contact_phone": "13800138000",
  "address_detail": "Building 3, Room 101"
}
// → { "address_id": "...", "display_name": "...", "lat": ..., "lng": ... }
```

You can also call `select_address` directly with an existing address's `address_id`. See [Search Addresses](/en/mcp/addresses/search) and [Select/Register Address](/en/mcp/addresses/select); edit door number / label with [`update_address`](/en/mcp/addresses/update) (the `address_id` stays the same).

### Phase 4: Quote Cart

```json
// tool: quote_cart — quote the cart, get quote_id
{
  "consent_grant_id": "cg_your_consent_grant",
  "shop_id": "<from search>",
  "cart_id": "<from search>",
  "address_id": "<from address>",
  "items": [
    {"item_id": "item_001", "sku_id": "sku_001", "quantity": 2, "ingredient_option_ids": []},
    {"item_id": "item_002", "sku_id": "sku_002", "quantity": 1, "ingredient_option_ids": []}
  ]
}
// → { "quote_id": "...", "can_checkout": true, "payable_price": 1500 }
```

`items` is an array (NOT a JSON string); each item's `item_id` / `sku_id` comes from `get_shop_menu`. `can_checkout` indicates whether min-order and other ordering conditions are met, and `payable_price` is the estimated payable (in cents). Full fields in [Quote Cart](/en/mcp/cart/quote).

### Phase 5: Preview Order (Pre-Order Confirmation)

<Check title="Production Best Practice - Confirm Before Ordering">
Always validate and show the final price with `preview_order` before creating the order to avoid mistakes. The `preview_id` + `confirmation_token` it produces are the credentials required to actually place the order.
</Check>

```json
// tool: preview_order — preview the order, get preview_id + confirmation_token
{
  "consent_grant_id": "cg_your_consent_grant",
  "shop_id": "<from search>",
  "cart_id": "<from search>",
  "address_id": "<from address>",
  "items": [
    {"item_id": "item_001", "sku_id": "sku_001", "quantity": 2, "ingredient_option_ids": []}
  ],
  "quote_id": "<from quote>",
  "order_remark": "Leave at door, please ring bell"
}
// → { "preview_id": "prv_...", "confirmation_token": "cf_...", "price": {...}, "available_coupons": [...] }
```

`preview_id` + `confirmation_token` must be used as a pair, are produced by the same preview, and are valid for about 10 minutes.

**Coupons take effect at the preview stage**, and the coupons actually usable for the current order are whatever is in the returned `available_coupons` (`coupon_ids` tri-state: omitted = auto-pick best; `[]` = no coupon; `["<coupon_id>"]` = specific coupon). To switch coupons, pick a `available_coupons[].coupon_id` and re-call `preview_order` with `coupon_ids=[...]` to re-price:

```json
// tool: preview_order — re-price after picking coupons
{
  "consent_grant_id": "cg_your_consent_grant",
  "shop_id": "<from search>",
  "cart_id": "<from search>",
  "address_id": "<from address>",
  "items": [
    {"item_id": "item_001", "sku_id": "sku_001", "quantity": 2, "ingredient_option_ids": []}
  ],
  "coupon_ids": ["<selected coupon_id>"]
}
// → { "preview_id": "prv_...", "confirmation_token": "cf_...", "price": {...}, "selected_coupons": [...] }
```

The account-level coupon list can be queried with [`list_coupons`](/en/mcp/coupons/list), but **what's actually usable for the current order is the `available_coupons` from `preview_order`**. Full fields and the `coupon_ids` tri-state are in [Preview Order](/en/mcp/orders/preview).

### Phase 6: Create Order

Place the order with the `preview_id` + `confirmation_token` from the same preview:

```json
// tool: create_order — create the order (confirmation_token is the idempotency key)
{
  "consent_grant_id": "cg_your_consent_grant",
  "preview_id": "prv_...",
  "confirmation_token": "cf_...",
  "callback_url": "https://your.app/callbacks/order"
}
// → { "order_id": "ord_...", "status": "...", "payment_action": {...} }
```

This tool uses `confirmation_token` as the **idempotency key**: a token can place only one order; re-ordering requires a fresh preview for a new token. Returns `order_id`, `status`, and (when payment is needed) `payment_action`. You may pass `callback_url`; the gateway polls order status and POSTs a callback once it leaves the unpaid state (`event=order_payment`, body carries `order_id`, `ispay`, `status`, etc.) — otherwise poll `get_order_status` yourself. Full fields in [Create Order](/en/mcp/orders/create).

### Phase 7: Password-Free Sign

The first order requires the user to complete password-free payment signing. Get the signing action:

```json
// tool: get_sign_action — get the password-free signing action (H5 link)
{
  "consent_grant_id": "cg_your_consent_grant",
  "order_id": "ord_..."
}
// → signing action: when action_type=open_h5 it carries action_url (H5 sign page); none means already signed
```

When `action_type=open_h5`, direct the user to `action_url` (the H5 sign page) to sign; `none` means already signed. Then poll the signing result with `get_sign_status`:

```json
// tool: get_sign_status — query the signing status
{
  "consent_grant_id": "cg_your_consent_grant",
  "order_id": "ord_..."
}
// → { "signed": ..., "status": "...", ... }
```

Full chain and fields in [Order Flow](/en/gateway/order-flow).

## Step 4: Handle Edge Cases

Robust Agents gracefully handle edge cases and provide friendly error messages. Gateway errors return a uniform `{"error": {"code", "message"}}` structure (every MCP tool returns this shape on failure).

### Error Handling

Branch on `error.code` to show friendly messages:

| Error code | Meaning | Suggested handling |
|------------|---------|--------------------|
| `AUTH_REQUIRED` / `AUTH_INVALID` | Connection-layer API Key missing or invalid | Check the `Authorization: Bearer clw_...` connection header |
| `CONSENT_GRANT_INVALID` / `CONSENT_GRANT_EXPIRED` | User consent invalid or expired | Re-initiate binding (`request_user_bind` → `verify_user_bind`) |
| `CAP_NOT_BOUND` | This Agent has not enabled the capability | Enable the capability for the Agent in the console |
| `PUBLIC_REFERENCE_INVALID` | Platform ID (shop / address / order) invalid, expired, or not the user's | Re-fetch the ID from the prior step; never fabricate or mix across chains |
| `RATE_LIMITED` / `QUOTA_EXCEEDED` | Too many requests or quota exhausted | Retry later with exponential backoff |
| `ELEME_ERROR` | Upstream service error | Ask the user to retry later, or degrade to cached results |

```python
# Illustrative: wrap one MCP tool result and branch on error.code
def handle_tool_result(result: dict):
    err = result.get("error")
    if not err:
        return result  # success, use it directly
    code = err["code"]
    if code in ("AUTH_REQUIRED", "AUTH_INVALID"):
        print("❌ Connection-layer API Key missing or invalid, check the Authorization header")
    elif code in ("CONSENT_GRANT_INVALID", "CONSENT_GRANT_EXPIRED"):
        print("❌ User consent invalid or expired, please re-initiate binding")
    elif code == "CAP_NOT_BOUND":
        print("❌ This Agent has not enabled the capability, enable it in the console")
    elif code == "PUBLIC_REFERENCE_INVALID":
        print("❌ Platform ID (shop / address / order) invalid, expired, or not the user's")
    elif code in ("RATE_LIMITED", "QUOTA_EXCEEDED"):
        print("❌ Too many requests or quota exhausted, retry later")
    elif code == "ELEME_ERROR":
        print("❌ Upstream error, retry later")
    else:
        print(f"❌ Tool error: {code} - {err.get('message')}")
    return None
```

### User Consent Expiration Handling

Any business tool returning `CONSENT_GRANT_INVALID` / `CONSENT_GRANT_EXPIRED` means re-authorization is needed (or proactively compare the recorded `expires_at`). Just run the binding flow again — **re-authorization rotates the grant**, so you get a new `consent_grant_id`; replace the stale value in local storage with it.

```
business tool returns CONSENT_GRANT_INVALID / EXPIRED
  → request_user_bind (get bind_id, user receives a code)
  → verify_user_bind (get a new consent_grant_id)
  → retry the original tool call with the new consent_grant_id
```

### Shop Closed Handling

The `available` / `unavailable_reason` in `search_shops` browse results let you pre-check whether a shop is open. If the order chain hits a closed shop mid-way, prompt the user to choose another shop and go back to `search_shops` to re-select.

### Order Query with Retry

`get_order_status` is a read-only query and is safe to retry on timeout:

```json
// tool: get_order_status — query the order (read-only, retryable)
{
  "consent_grant_id": "cg_your_consent_grant",
  "order_id": "ord_..."
}
// → { "status": "...", "status_text": "...", "paid_at": ..., "delivery": {...} }
```

Use bounded backoff retries (e.g. up to 3) for read-only tools like `get_order_status`, but **do not blindly retry order-creation tools** — rely on the `confirmation_token` idempotency key to avoid duplicate orders.

## The Full Chain at a Glance

Chaining the tool calls from each step above gives one complete order:

```
request_user_bind / verify_user_bind  → consent_grant_id
search_shops (get shop_id + cart_id)
get_shop_menu (get item_id / sku_id)
quote_cart (get quote_id)
select_address (get address_id)
preview_order (get preview_id + confirmation_token)
create_order (get order_id)
get_sign_action (password-free sign) → get_order_status (query status)
```

All cross-step IDs (`shop_id` / `cart_id` / `address_id` / `preview_id` / `confirmation_token` …) are issued by the gateway and must be passed **verbatim** — never fabricate them or mix across chains. `confirmation_token` is the order idempotency key, and the `consent_grant_id` minted during binding is the user-consent argument carried by every subsequent business tool call.
