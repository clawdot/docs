## Per-Grant Binding and Isolation

The security foundation of the Skills Platform is **per-grant binding**: each user consent grant binds "one Agent + one authorized user + one capability" into an exclusive, non-overlapping triple. This design naturally isolates the data and permissions of different Agents and different users, eliminating the need for a complex centralized permission management system.

**Core features:**

- **Natural isolation**: Each consent grant's user data is only visible to the Agent it is bound to; cross-Agent access is permanently blocked
- **No privilege creep**: No special roles like Admin or Super User; permissions are explicit, fixed, and scoped by capability
- **Audit-friendly**: Each grant relationship is clear and easy to trace, facilitating log auditing and compliance checks

## Two-Layer Authentication

The Skills Platform uses an **API Key + user consent grant** two-layer authentication mechanism:

1. **API Key** — Identifies the Agent, managed by the Agent application provider
2. **User consent grant** — Identifies the authorized delivery user, obtained through the binding flow (SMS code / H5)

### API Key (Agent Identification)

- **Prefix**: Starts with `clw_`, followed by random characters, e.g. `clw_a1b2c3d4...`
- **Storage**: Server only stores a hash, never plaintext; each request is compared by hash
- **Issuance**: Generated when creating an Agent in the [Portal](http://console.hicaspian.com), **displayed only once** — if lost, regenerate it
- **Usage**: In all requests' HTTP Header as `Authorization: Bearer {API_KEY}`; same for MCP and REST

### Consent Grant (User Identification)

- **Prefix**: Starts with `cg_`
- **Source**: Obtained after the user authorizes through the binding flow (SMS code / H5); `verify_user_bind` (`POST /auth/bind/verify`) returns `consent_grant_id`, `scopes`, and `expires_at` (ISO 8601) on success
- **Storage**: The plaintext is returned only once; only a hash is stored — keep it safe
- **Transport**:
  - **REST:** via the `X-Consent-Grant-Id` header (never in the JSON body)
  - **MCP:** as the `consent_grant_id` argument on each tool (not a header)
- **Invalidation**: Once `expires_at` is reached, or after being revoked via `revoke_user_bind` (`POST /auth/unbind`), it is immediately invalid on all endpoints; re-bind to obtain a new one

## Data Encryption

The Skills Platform applies layered encryption / hashing to all sensitive data, ensuring that even if the database is breached, critical information cannot be directly recovered:

<Tabs>
  <Tab title="User Identity">
    **User ID Encryption**
    - Algorithm: AES-256-GCM
    - Key: Generated and managed securely by the server
    - Scenario: User ID stored as ciphertext in the database
    - Decryption permission: Only the bound Agent can decrypt its corresponding user data
  </Tab>

  <Tab title="Phone Number">
    **Phone Number De-duplication / De-identification**
    - Algorithm: SHA-256 (one-way hash)
    - Purpose: Detect duplicate bindings, de-identified storage
    - Feature: One-way hash, cannot be decrypted in reverse
    - Scenario: After binding verification, the phone number is stored as a hash
  </Tab>

  <Tab title="Credential Hashing">
    **API Key and consent grant hashing**
    - Algorithm: One-way hash
    - Purpose: Verify the legitimacy of the Agent and the user consent
    - Feature: Plaintext credentials cannot be viewed in the database
    - Scenario: On each request, the server hashes the incoming API Key / consent_grant_id and compares with the database
  </Tab>
</Tabs>

## Agent-User Isolation

The Skills Platform enforces strict isolation policies at the data access layer:

```
Access Rules:
┌─────────────────────────────────────────────┐
│ Agent A's API Key + consent grant 1         │
│ → Can only access User 1's data             │
│ → Cannot access User 2's data               │
│ → Cannot access Agent B's data              │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│ Agent B's API Key + consent grant 2         │
│ → Can only access User 2's data             │
│ → Cannot access User 1's data               │
│ → Cannot access Agent A's data              │
└─────────────────────────────────────────────┘
```

**Implementation Details:**

1. Every authorized request carries an API Key and a `consent_grant_id`
2. The server verifies the API Key and resolves the `agent_id`
3. The server verifies the `consent_grant_id`, locating the authorized user and its granted capability
4. Database query condition: `WHERE agent_id = ? AND user_id = ?`
5. Any query crossing these two conditions is rejected (a grant for another capability / provider returns `CONSENT_GRANT_WRONG_CAP`; a capability not enabled returns `CAP_NOT_BOUND`)

**Key milestones:**

| Event | Trigger | Description |
|-------|---------|-------------|
| Minted | `verify_user_bind` succeeds | Returns `consent_grant_id` + `scopes` + `expires_at`; plaintext only this once |
| Normal use | Before `expires_at` | Authorized requests processed normally |
| Re-authorization rotates | The same user binds successfully again | Mints a new `consent_grant_id`, the old one is immediately invalidated |
| Invalidated | `expires_at` reached or revoked | Immediately invalid; requests return `CONSENT_GRANT_INVALID` / `CONSENT_GRANT_EXPIRED` |
| Re-bind | After invalidation | Re-run the binding flow for a new one; the user's addresses, order history, etc. are kept and become available again after re-authorization |

## Authentication Failure Handling

Auth / authorization failures return a uniform `{"error": {"code", "message"}}` structure with the appropriate HTTP status code:

<CardGroup cols={2}>
  <Card title="401 Unauthorized" icon="lock">
    **Missing or invalid credentials**
    - Missing API Key (`AUTH_REQUIRED`)
    - API Key invalid or disabled (`AUTH_INVALID`)
    - Missing consent_grant_id (`CONSENT_GRANT_REQUIRED`)
    - consent_grant_id invalid or expired (`CONSENT_GRANT_INVALID` / `CONSENT_GRANT_EXPIRED`)
  </Card>

  <Card title="403 Forbidden" icon="ban">
    **No permission to access**
    - Grant belongs to another capability / provider (`CONSENT_GRANT_WRONG_CAP`)
    - This Agent has not enabled the capability (`CAP_NOT_BOUND`)
  </Card>

  <Card title="429 Too Many Requests" icon="hourglass">
    **Rate limiting**
    - Too many requests within the window (`RATE_LIMITED`)
    - Each Agent is rate-limited independently (create order 10/min, others 60/min)
  </Card>

  <Card title="Unified error format" icon="circle-x">
    **`{"error": {"code", "message"}}`**
    - All auth / authorization / business errors share this shape
    - Full error code list in [Error Handling](/en/gateway/error-handling)
  </Card>
</CardGroup>

## Security Best Practices

<Tabs>
  <Tab title="Agent Application Side">
    - **Protect the API Key**: Store it in secure environment variables or a key management system, never commit to version control
    - **Protect the consent_grant_id**: Store the user consent credential securely (plaintext returned only once) — it involves sensitive user data
    - **HTTPS only**: All communication with the Skills API must use HTTPS
    - **Rotation and revocation**: Rotate / disable the API Key in the Portal as needed (effective immediately); the consent grant rotates on re-authorization and can be revoked any time via `revoke_user_bind`
    - **Error handling**: Catch 401/403 errors and prompt the user to re-authenticate or re-bind
  </Tab>

  <Tab title="Server Side">
    - **Verify all requests**: Never trust client-claimed identity; always verify the API Key and consent_grant_id
    - **Log sanitization**: Do not record the full API Key or consent_grant_id in logs, only a prefix or hash
    - **Rate limiting**: Each Agent has an independent rate limit to prevent abuse
    - **Key rotation**: Periodically rotate database keys with smooth transition of old keys
    - **Audit log**: Record all authentication attempts (successful and failed) for compliance checks
  </Tab>

  <Tab title="Binding Flow">
    - **Replay attack prevention**: SMS codes are one-time use, preventing duplicate submission
    - **Attempt limiting**: Lock a phone number for a period after exceeding a number of failed verifications
    - **Code expiration**: Generated verification codes auto-expire after a few minutes
    - **Number validation**: Validate phone number format to prevent malicious input
    - **H5 callback validation**: In H5 authorization mode, validate the callback source to prevent forgery
  </Tab>
</Tabs>

## FAQ

<details>
<summary>Can one consent grant be used across multiple Agents?</summary>

**No**. A consent grant binds an "Agent + user + capability" triple and is only valid for the Agent that minted it. Each Agent application provider must run the binding flow separately for that user to obtain its own `consent_grant_id`. Cross-binding access is rejected (`CONSENT_GRANT_WRONG_CAP`).

</details>

<details>
<summary>What if the API Key is leaked?</summary>

Immediately disable that API Key in the [Portal](http://console.hicaspian.com); the system will automatically stop all requests using it. Then generate a new API Key and update your application configuration. The database only stores the API Key's hash, so attackers cannot directly leverage a leaked hash.

</details>

<details>
<summary>Will data be lost if a consent grant expires or is revoked?</summary>

**No**. A consent grant is just an access credential; after expiration or revocation, the user re-runs the binding flow (same phone number) to obtain a new `consent_grant_id`, and the addresses, order history, etc. are kept and become available again after re-authorization — nothing is deleted because the credential expired.

</details>

<details>
<summary>Does it support API Key permission levels?</summary>

The Skills Platform does not provide API Key permission levels. Access scope is bounded by each consent grant's capability (scope) — a grant can only operate on data for its bound user under its own capability. If fine-grained permission control is needed, implement it at the Agent application layer.

</details>
